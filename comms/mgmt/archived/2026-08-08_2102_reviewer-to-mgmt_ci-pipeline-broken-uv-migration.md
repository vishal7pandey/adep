## Finding

```text
Finding ID: REV-003
Severity: high
Category: reliability or operational risk / process or closed-loop failure
Confidence: high
Review pass: Pass 1 — reliability, observability, operations, deployment, CI/CD
Affected areas: .github/workflows/ci.yml, requirements.txt,
requirements-dev.txt (removed), pyproject.toml, uv.lock

Executive finding:
The GitHub Actions CI workflow's backend job still runs
`pip install -r requirements-dev.txt`, but that file was deliberately
deleted as part of the uv migration (archived message
`comms/mgmt/archived/2026-08-08_1340_backend-to-mgmt_uv-migration-complete.md`,
step 5: "Removed requirements-dev.txt — dev deps now in pyproject.toml").
The CI job's dependency-install step will fail outright, so lint, type
check, tests, and coverage do not currently run in CI on any push to
main or any pull request.

Evidence:
- `.github/workflows/ci.yml` lines 24-26 (backend job, "Install
  dependencies" step):
  `pip install -r requirements.txt` then
  `pip install -r requirements-dev.txt`.
- `requirements-dev.txt` does not exist anywhere in the repository
  (workspace file search returned zero matches).
- `requirements.txt` is now an autogenerated uv export
  (`# This file was autogenerated by uv via ... uv export
  --format requirements-txt`) and begins with `-e .`, i.e. it is not
  the file the project's own tooling standard (PROTOCOL.md §10.1)
  expects CI to install from — the migration message explicitly lists
  updating docs and error messages but the migration's own acceptance
  criteria ("No pip install commands in any scripts or docs") was
  checked off without updating `.github/workflows/ci.yml`, which still
  uses two `pip install` commands.
- The uv-migration message was reviewed and archived by mgmt
  ("Processed by mgmt. Completion confirmed and item moved to
  implemented/") without this discrepancy being caught.

Impact:
Every push to `main` and every pull request currently fails CI at the
dependency-install step, before lint, mypy, pytest, or the
`--cov-fail-under=80` coverage gate ever run. This means the "958
tests passing" and "Frontend build clean" claims in
`projectmgmt/STATUS.md` are not currently being verified by the stated
CI/CD pipeline on an ongoing basis — they reflect local/manual `uv run
pytest` runs, not automated gate enforcement. Any regression introduced
after the uv migration would not be caught by CI.

Why this matters:
This is a closed-loop process failure, not just a config typo: the
migration had an explicit acceptance criterion for exactly this
("No pip install commands in any scripts or docs"), the criterion was
marked complete, and the completion was reviewed and archived by
management — yet the CI workflow file was not part of that check. The
project currently has no working automated quality gate, which
directly undermines every other "tests pass" claim used to justify
completion of subsequent backlog items.

Recommended management action:
Assign a small, immediate backend fix: update
`.github/workflows/ci.yml` to install dependencies via `uv sync
--all-extras` (or equivalent) and run lint/type-check/tests/coverage
via `uv run ...`, consistent with PROTOCOL.md §10.1. Recommend
re-verifying CI green on a real PR before treating any further backend
work as CI-validated, and consider adding a lightweight repo audit
step (e.g. "does CI still reference deleted files") to the closed-loop
review checklist for future migrations.

Suggested ownership:
Backend, with management verification that the next PR actually goes
green in the Actions tab (not just local test runs).

Validation required:
Open a PR (or push to main) after the fix and confirm the backend CI
job completes successfully through the coverage step, not just up to
dependency install.

Confidence and limitations:
Confirmed by direct inspection of `.github/workflows/ci.yml`, a
workspace-wide file search confirming `requirements-dev.txt` no longer
exists, and the archived migration message describing its removal.
This review did not have access to the GitHub Actions run history for
this repository, so the actual failing run was not observed directly —
confidence is based on the workflow definition and file-existence
evidence, which is unambiguous.

Related findings:
None found.
```
