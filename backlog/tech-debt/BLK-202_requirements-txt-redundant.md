## Description

`requirements.txt` is 2,991 lines long and was auto-generated by `uv export --format requirements-txt --output-file requirements.txt` (as stated in its first line). The project already has `pyproject.toml` (source of truth) and `uv.lock` (lockfile). The `requirements.txt` file is a derived artifact that can be regenerated on demand.

It's currently only used by the `Dockerfile` (see BLK-195) — everything else uses `uv sync`.

## Problem Statement

- Three dependency manifests exist when two suffice (`pyproject.toml` + `uv.lock`)
- `requirements.txt` can go stale if someone updates `pyproject.toml` but forgets to re-run `uv export`
- 2,991 lines of hashed pins add noise to diffs, PRs, and repo size
- It creates confusion about which file is authoritative — a contributor might edit `requirements.txt` directly instead of `pyproject.toml`

## Acceptance Criteria

- [ ] Remove `requirements.txt` from the repo
- [ ] Update `Dockerfile` to use `uv sync` instead of `pip install -r requirements.txt` (see BLK-195)
- [ ] Add `requirements.txt` to `.gitignore` to prevent accidental re-commits
- [ ] Document in CONTRIBUTING.md that `requirements.txt` can be generated via `uv export` if needed for non-uv environments

## Constraints

- Don't remove until BLK-195 is resolved (Dockerfile currently depends on it)
- If a non-uv environment is needed (e.g., a server without uv), document how to generate it on demand

## Dependencies

- `requirements.txt`
- `pyproject.toml`, `uv.lock`
- Related to BLK-195 (Dockerfile uses pip instead of uv) — resolve that first
