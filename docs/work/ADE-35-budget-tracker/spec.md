# ADE-35 — Engine: budget tracker (turns/cost/time accounting)

Status: spec-approved · Risk: low · Jira: ADE-35
Created: 2026-10-05 · Slug: budget-tracker

Part of the ADE-30 vertical slice (`docs/work/ADE-30-engine-vertical-slice/spec.md`). No dependency on
the other stories; pure accounting logic, no I/O.

## Problem

The new engine needs the agent to reason about its own remaining turns/cost/time so it can decide when to
batch work (crop wider regions covering several entities per call) versus when to stop and serialize.
Nothing in ade today tracks this per-run; the old LangGraph engine's budget handling (if any) is internal
to its own graph nodes and not reusable by the new loop.

## Users and context

The new engine's `budget_status` tool (ADE-39) and every perception tool wrapper, which records its own
cost before delegating. Grounded in reading ade2's `src/ade2/budget.py` in full — the reference
implementation. Nothing here is on ADE-12's do-not-port list; it's generic accounting, not one of the
flagged defects.

## Goals and non-goals

**Goals**
- Track turns, dollar cost, and wall-clock seconds spent in a single extraction run.
- Per-tool-type cost table: free/local tools (validation, serialization, planning) cost 0 turns;
  perception tools (survey, crop, OCR) cost 1 turn plus a dollar estimate.
- Return actionable recommendation strings once a resource is running low, not just raw numbers.
- Scale a starting budget to a document's complexity (zone count, resolution) rather than one fixed
  constant for every document.

**Non-goals**
- Enforcing the budget (stopping the agent mid-run) — this module only reports status; ADE-39's agent
  loop decides what to do with that information, same as ade2's design (the agent reads `budget_status`
  and reasons about it itself).
- Real-money billing or metering — `cost_usd` is an estimate for the agent's own planning, not an
  accounting-system source of truth.

## Requirements

- R1. `Budget` (max turns, max cost, max seconds) and `Spend` (accumulated turns, cost, seconds) are
  separate dataclasses; `Spend.remaining(budget)` and `Spend.fraction_used(budget)` compute derived views
  without mutating either.
- R2. `BudgetTracker.record_tool(name)` looks up a per-tool-type cost (turns + dollars) from a module-level
  table and accumulates it into `Spend`; an unlisted tool name defaults to costing 1 turn (conservative,
  matches ade2).
- R3. `BudgetTracker.status()` returns remaining turns/cost/seconds, fraction used per resource, the full
  tool-call history, and zero or more recommendation strings, generated by threshold rules (e.g. "only N
  turns left, stop surveying and serialize").
- R4. `estimate_budget_for_complexity(zone_count, image_pixels)` produces a `Budget` scaled to a
  document's apparent complexity, with the scaling capped so a pathological zone count can't produce an
  unbounded budget.

## Acceptance criteria

- AC1. (R1) `Spend(turns=5).remaining(Budget(max_turns=10))` returns `turns=5`; `fraction_used` on the
  same returns `turns: 0.5`. Neither call mutates the `Spend` or `Budget` instances.
- AC2. (R2) Recording three `crop_and_read_tool` calls and one `validate_extraction` call against a fresh
  `BudgetTracker` leaves `spend.turns == 3` (the free tool contributes 0) and `spend.cost_usd` equal to
  exactly 3× the configured crop cost (no contribution from the free tool).
- AC3. (R2) Recording a tool name not in the cost table costs exactly 1 turn and $0.00 (the documented
  default), not an error.
- AC4. (R3) With `max_turns=10` and 8 turns spent, `status()["remaining_turns"] == 2` and
  `recommendations` contains at least one string (the low-turns-left threshold); with 2 turns spent, no
  recommendation about low turns appears.
- AC5. (R4) `estimate_budget_for_complexity` returns a larger `max_turns` for `zone_count=20` than for
  `zone_count=2` (same pixel count), and the same `image_pixels=10_000_000` vs `image_pixels=500_000` at
  equal zone count produces a larger budget for the higher-resolution input — but an absurd
  `zone_count=10_000` does not produce an unbounded `max_turns` (capped).
- AC6. Hermetic unit tests: pure arithmetic, no I/O, no network, no timing-dependent assertions beyond
  what `time.time()`-based `seconds` tracking requires (use a controllable/mockable clock or tolerate a
  wide timing window rather than asserting exact elapsed seconds).

## Edge cases and failure modes

- `max_turns=0` or `max_cost_usd=0.0` (a degenerate/exhausted budget passed in): `remaining()` returns
  zero, not negative; `fraction_used` does not divide by zero (guard the denominator, matching ade2's own
  `if budget.max_turns else 0.0` pattern).
- Recording tool calls after the budget is already exhausted: still records (the tracker never refuses a
  record — it only reports status); the agent decides what to do, this module doesn't enforce.

## Non-functional requirements

- Observability: `logger = logging.getLogger(__name__)`; `estimate_budget_for_complexity` logs the
  computed budget at INFO (useful for understanding why a given run got the budget it did).

## Assumptions

- The per-tool cost table and thresholds are ported with the same values ade2 used (observed-data-based:
  ~$0.04/crop_and_read, ~$0.03/survey call) as a starting point; they are not re-derived from ade's own
  pricing in this story — ADE-31's head-to-head evaluation is where real cost data will show if these
  need adjusting.

## Risks and dependencies

- Risk: low — pure accounting, no I/O, no model calls.
- Depends on: nothing. Used by: ADE-39 (the engine loop's `budget_status` tool and every tool wrapper).
