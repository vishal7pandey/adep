# ADE-56 — Contain batch and VLM image paths (Sonar S2083 ADE-56, ADE-57)

Status: draft · Risk: high · Jira: ADE-56
<!-- Security finding: neutral wording on purpose; this repo is public. -->

Covers two SonarCloud findings, one rule (`pythonsecurity:S2083`, BLOCKER vulnerability): ADE-56 (Sonar issue
`AaESHl-HjNIvKL1jZh79`, `src/api/routes/batches.py:53`, `save_batch`) and ADE-57 (Sonar issue `AaESHmAUjNIvKL1jZh9X`,
`src/providers/vlm_azure.py:60`, `_encode_image`). ADE-56 is the key of this work item; ADE-57 closes separately on its own
re-queried Sonar issue. Only these two issues are in scope; other Sonar issues and the CodeQL path-injection alerts belong to a
later sweep.

## Repro

Environment / version / commit where it fails: `master` @ 487aaef, Python 3.14 venv, Windows; platform independent except where noted.

Automated repro (failing tests, with the command to run them):

- `src/tests/test_sonar_path_containment.py`, run `uv run python -m pytest src/tests/test_sonar_path_containment.py -q`.
  On current code 7 of 14 tests fail, 6 pass (they pin legitimate behaviour) and 1 is skipped when symlinks are not permitted:
  - `TestSaveBatchContainment::test_relative_traversal_id_is_rejected_and_nothing_is_written`,
    `::test_sibling_dir_sharing_the_batches_name_prefix_is_rejected` and
    `::test_absolute_id_is_rejected_and_nothing_is_written`: `save_batch` does not raise (DID NOT RAISE `ValueError`) and writes a
    `.json` file outside `.adep/batches/`.
  - `TestImagePathContainment::test_absolute_path_outside_both_roots_is_refused`,
    `::test_relative_traversal_out_of_the_working_dir_is_refused` and
    `::test_sibling_dir_sharing_the_working_dir_name_prefix_is_refused`: `vlm()` reads the file and sends it to the model client
    (`ok` is `True`, the client is called) instead of refusing.
  - `::test_encode_image_raises_for_a_path_outside`: `_encode_image` DID NOT RAISE `ValueError`.

Reproducibility: always.

## Expected

- `save_batch(batch_id, ...)` only ever writes `<cwd>/.adep/batches/<batch_id>.json`; an id that resolves anywhere else is refused
  with `ValueError` and nothing is written.
- `_encode_image(image_path)` only reads an image under the working directory tree (where `.adep/documents/<id>/page_NNN.png` and
  the `sample-data/` fixtures live) or under the system temp directory (where the engine writes survey images and crops
  with `tempfile.mkstemp`). Any other path is refused with `ValueError`; `vlm()` and the other callers turn it into the tool's
  normal failure result (`ok=False`) at once, without the model-call retry and backoff, and the model client is never called.
- Legitimate inputs behave as before.

## Actual

- `save_batch` builds `Path.cwd()/.adep/batches/f"{batch_id}.json"` from the id and calls `write_text` with no containment
  check. The id reaches it from the URL (`POST /batches/{batch_id}/cancel` loads the batch, then saves it), so an id that resolves
  outside the directory (a path separator in a single URL segment on Windows, or an absolute id) overwrites a `.json` file there.
- `_encode_image` calls `open(image_path, "rb")` on a string that is the agent's `image_path` tool argument (registered tool
  `vlm`, `read_table`, `read_chart` take it from the model's tool call) or a caller-supplied page path, so any readable file
  can be base64-encoded and sent to the model provider.

## Root cause (with evidence)

- Where: `src/api/routes/batches.py:46-53` (`_batch_path`, `save_batch`) and `src/providers/vlm_azure.py:58-63` (`_encode_image`).
- Why it fails: a value that comes from outside (URL path segment, LLM tool argument) is joined into or used as a filesystem
  path and used at the file operation without first resolving it (`os.path.realpath`) and proving it stays inside the intended
  base directory.
- Introduced by: always present (original implementations).
- Evidence: the 7 failing tests above; SonarCloud S2083 flows end at `batches.py:53` (taint from the `cancel_batch` route
  through `load_batch` and `save_batch`) and at `vlm_azure.py:60` (taint from `classify.py:241` and the tools through `_call_vlm`).

## Blast radius

- Other callers of `save_batch`: `create_batch` (id generated by `uuid`), `update_batch` (id from a loaded batch), and
  `cancel_batch` (id from the URL). All go through the one guarded function. `load_batch`, `_batch_path` and `delete_batch`
  use the same joined path; they are separate findings (`delete_batch` is a CodeQL alert) and stay for the later sweep.
- Other callers of `_encode_image` (via `_call_vlm`): `vlm`, `read_chart`, `read_table`, `src/tools/classify.py`,
  `src/engine/tools.py` (page paths from the document store, temp survey images, crops written with `tempfile.mkstemp`),
  `src/tools/graph/*`, `signature_detection.py`, `table_detection.py`. All of them pass paths under the working directory tree
  (`.adep/`, `sample-data/`) or the system temp directory; the allowed roots are exactly those two.
- A user who runs the app from a directory and points a tool at an image elsewhere on disk gets a refusal now (documented
  behaviour change); the demo and evaluation data are inside the repository.
- Exposure: batch routes are open when auth is off (local dev default); the VLM tools are reachable from the agent loop. Data
  already affected: none known.

## Regression criterion (AC1)

AC1: The failing tests in `src/tests/test_sonar_path_containment.py` pass after the fix and fail on the current code: for
`save_batch` and for `_encode_image` / `vlm()`, an input that escapes the intended directory is refused (`ValueError`, or
`ok=False` from `vlm`), nothing is written outside `.adep/batches`, and the model client is never called for it.

AC2: Legitimate behaviour is unchanged: saving, overwriting and loading a batch; an image under the working directory or under
the system temp directory is still read and sent (PNG and JPEG MIME types as before); the rest of the backend suite stays at its
known baseline (`-m "not integration"`: only ADE-23 and ADE-24 fail).

AC3: After the fix is merged and the push scan on `master` has run, the SonarCloud API
(`https://sonarcloud.io/api/issues/search?issues=<key>&componentKeys=vishal7pandey_adep`) shows both issues closed
(`AaESHl-HjNIvKL1jZh79` for ADE-56, `AaESHmAUjNIvKL1jZh9X` for ADE-57; verified after merge, the Jira tickets close only on that).

## Fix constraints

- Containment is checked inline at the point of use with the pattern that closed the equivalent CodeQL and chatpid findings:
  `os.path.realpath` on the base and on the candidate, then `candidate.startswith(base + os.sep)`, before the file is opened;
  the opened path is the checked string. No shared helper (the sanitizer must stay visible to the scanner at each sink).
- Minimal diff: `save_batch` in `src/api/routes/batches.py`, `_encode_image` and the retry predicate of `_call_vlm` in
  `src/providers/vlm_azure.py`, the new test file, and this work item folder. No API shape change.
- A refusal is not retried: `_call_vlm` keeps its retry on transient failures but does not retry the refusal.
- Do not touch other findings or unrelated files.

## Risks

- Risk high: security fix on a file-writing route and on the model-input path. A legitimate image outside the working directory
  and temp directory is now refused (see Blast radius). Rollback: revert the merge commit.
- If SonarCloud does not recognise the inline check the issue stays open; then the fix is improved (not dismissed) and the
  tickets stay open meanwhile.
